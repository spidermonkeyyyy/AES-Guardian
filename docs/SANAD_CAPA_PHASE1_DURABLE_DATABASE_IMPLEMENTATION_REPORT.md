## Result

Exact-ID recovery, authorization, acknowledgement, and reset ordering are implemented. The Create screen was not changed.

## Implementation details

- Migration 9 creates `capa_creation_operations` with operation-ID primary key, creator and CAPA foreign keys, unique reference and linked-action constraints, pending/committed state check, one-pending-operation-per-creator partial unique index, and status index.
- Migration 10 adds nullable `acknowledged_at` and the unacknowledged-operation index. Existing schema-8 CAPAs are not backfilled or otherwise changed.
- Reservation normalizes the payload and binds its canonical JSON and SHA-256 hash to the explicit `new` or `retry` intent. New IDs must be valid UUID-v4 values generated by the existing secure utility; entropy failure propagates without a weak fallback. A `new` ID collision fails, and retry requires an existing exact creator/payload reservation.
- Stage B reloads and checks the creator and operation inside the transaction, then atomically inserts the CAPA, audit entry, notification, and committed link. Known CAPA-reference collisions are handled narrowly; unknown database errors propagate. Failed Stage B writes leave the independent reservation pending when rollback succeeds.
- Reconciliation and committed-operation lookup verify the exact operation, linked CAPA payload/reference/creator, one matching audit record, and one matching notification. Recovery and acknowledgement are role-checked. Acknowledgement requires successful reconciliation, persists `acknowledged_at`, reads it back, and is idempotent.
- `createPreventionAction` retains its existing call signature and now delegates to the durable operation path. Legacy reference-only reconciliation remains limited to unlinked legacy CAPAs.
- Demo reset deletes operation rows before linked CAPAs and does not create operation rows for seeded CAPAs.
